<!-- sdlc:auto:start overview -->
HRMS_test is a scaffold generated by the Quorq AI SDLC platform for an HR management portal (employee, timesheet, leave and approval workflows across Employee/Manager/HR/Admin roles). The repository has two independent apps: a `frontend/` Vite + React 19 SPA whose screens were already reviewed and approved and currently render seeded sample data, and a `backend/` FastAPI 0.115 service that has no business logic yet -- only a `/health` endpoint and the scaffolding (SQLAlchemy models/Base, Pydantic stub schema, router package) for routes to be added later. The backend defaults to a local SQLite file so it runs with no database server; `docker-compose.yml` additionally defines Postgres and Redis containers for when a real architecture is wired in.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js (for the Vite/React frontend, npm scripts)
- Python 3.12 (matches backend/Dockerfile base image)
- pip
- Docker and Docker Compose (optional, for the Postgres/Redis services in docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. Copy .env.example to .env and fill in any required values
3. cd frontend && npm install
4. cd backend && pip install -r requirements.txt
5. (optional) from the repo root, run docker compose up -d to start Postgres and Redis if the backend is configured to use them via DATABASE_URL
6. Start the backend (uvicorn) and the frontend (vite dev server) as described in Run Commands
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend: one FastAPI router per architecture component that owns endpoints, under backend/app/routers/
- Backend: every not-yet-implemented route returns a typed StubResponse (schemas.py) instead of erroring, keeping the service startable and its OpenAPI spec complete
- Backend: SQLAlchemy models inherit from the shared Base in app/database.py; tables are created via Base.metadata.create_all on app startup (no migrations yet)
- Backend: one DB session per request via the get_db dependency, closed in a finally block
- Backend: DATABASE_URL env var selects the database, defaulting to a local SQLite file
- Backend: CORS origins are configured via the ALLOWED_ORIGINS env var (comma-separated), falling back to the Vite dev server origins in development
- Frontend: screens live under src/screens (per README) and are written against the shared component/icon vocabulary in src/lib/ui.tsx and src/lib/icons.tsx
- Frontend: all API calls go through the apiFetch helper in src/lib/api.ts, which attaches a bearer token (session token if set, else VITE_API_SECRET_KEY) and reads VITE_API_BASE_URL
- Frontend: path alias @ maps to src/ (configured in both vite.config.ts and tsconfig.json)
- Frontend: component tests sit beside the components they test and are picked up by Vitest's src/**/*.{test,spec} glob; Playwright specs live separately in e2e/
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend can't reach the backend / CORS errors in the browser console | Set ALLOWED_ORIGINS on the backend to the frontend's origin, and set VITE_API_BASE_URL on the frontend to the backend's URL |
| `npm run build` succeeds but the app has type errors | Run `npm run typecheck` (tsc --noEmit) separately -- build does not typecheck |
| Playwright e2e tests fail to start a browser | Run `npm run test:e2e:install` first to fetch Chromium |
| Backend has no persistent/shared data between restarts or environments | Set DATABASE_URL to point at the Postgres instance from docker-compose.yml instead of relying on the default local SQLite file |
| `docker compose up` port conflict on 6379 | Both the `redis` and `redis-queue` services map container port 6379 to host port 6379; only one can bind that host port, so adjust one service's port mapping before starting both |
